# วัดผลแต่ละเคสเป็นตัวเลขยังไง

เขียน 2026-09-11 คู่กับตาราง 9 เคสในแผนหน้างาน

## ก่อนอื่น มีสาม error ไม่ใช่อันเดียว

สับสนสามอันนี้คือเหตุที่วันทดสอบได้ตัวเลขมาแล้วเอาไปตัดสินใจอะไรไม่ได้

```text
goal error          หยุดตรงไหน เทียบกับที่สั่งให้ไปหยุด  ทั้งคู่ในกรอบ map
                    เป็นเลขของ controller กับ goal checker
                    สคริปต์วัดได้  แต่จะน้อยกว่า xy_goal_tolerance เสมอ
                    โดยธรรมชาติ ต้องดูการกระจายของสิบรอบ ไม่ใช่รอบเดียว

drift correction    AMCL ต้องดึง odometry กลับเข้าแมพเท่าไร คือ map->odom
                    สคริปต์วัดได้ ไม่ต้องใช้ตลับเมตร
                    เป็นเลขที่ตอบว่า AMCL อย่างเดียวพอไหมบนหุ่นตัวนี้

localisation error  หุ่นอยู่ตรงไหนจริง เทียบกับที่หุ่นคิดว่าตัวเองอยู่
                    ** วัดจากในหุ่นไม่ได้เลย **
                    ทุก topic อยู่ใต้ความเชื่อที่กำลังถูกตรวจ
                    หุ่นที่มั่นใจแต่ผิด จะรายงานเลขสวย
                    อันนี้ต้องวัดจากพื้น เทปกาวจุดเริ่ม เทปกาวจุดหยุด วัดระหว่างสองจุด
```

เลขจากสคริปต์ช่วยคัดว่ารอบไหนควรเอาตลับเมตรไปวัด ไม่ได้แทนตลับเมตร

## ตั้งค่าก่อนวันวัด

**อ่าน `map -> base_link` จาก TF ไม่ใช่จาก `/amcl_pose`** AMCL ส่ง pose เฉพาะตอน
อัปเดต ซึ่งเกิดทุก `update_min_d` เมตร ตอนนี้ตั้ง 0.20 แปลว่าหุ่นที่หยุดแล้วถือ pose
เก่าได้ถึง 20 ซม. ซึ่งใหญ่พอ ๆ กับ error ที่จะวัด TF เป็น interpolate ต่อเนื่อง
`testcase_recorder` อ่านจาก TF ให้แล้ว

**รอบที่จะวัด ให้ลด `update_min_d` กับ `update_min_a` เหลือ 0.05** ใน
`config/amcl_livox.yaml` **ก่อน launch** ปรับสดไม่ได้ — Foxy อ่านค่าครั้งเดียวตอน
`on_configure` สั่งทีหลังตอบ success แต่ไม่มีผล เสร็จแล้วค่อยตั้งกลับ

```yaml
update_min_d: 0.05      # จาก 0.20 เฉพาะรอบวัด
update_min_a: 0.05      # จาก 0.10
```

CPU เพิ่มขึ้นเพราะ resample ถี่ขึ้น บอร์ด 8 คอร์ใช้อยู่ 1.59 มีที่เหลือพอ
แต่ดู `measure_board_load.sh` ระหว่างรอบแรกด้วย

## เคสเสา · วัด inflation จริงว่ากว้างเท่าไร

หลักการ **ตั้ง goal ทับตัวเสาเลย** goal นั้นไปไม่ถึงแน่นอน หุ่นจะเดินเข้าไปจนถึง
ขอบที่ costmap ห้ามแล้วไปต่อไม่ได้ ระยะที่มันเข้าใกล้ที่สุดคือขอบ inflation จริง
ไม่ใช่ค่าที่เขียนใน yaml

### วิธีสั่ง

```bash
# 1 หุ่นยืนที่จุดเริ่ม ติดเทปกาวที่พื้นใต้กลางตัวหุ่น
#   วางเสาตรงหน้าหุ่นพอดี วัดด้วยตลับเมตรให้ได้ 4.00 ม. เป๊ะ

# 2 อ่านพิกัดจุดเริ่มของหุ่น
ros2 run go2_control record_waypoint

# 3 คำนวณพิกัดเสา จาก x0 y0 yaw0 ที่ได้
#   goal_x = x0 + 4.0*cos(yaw0)
#   goal_y = y0 + 4.0*sin(yaw0)

# 4 เริ่มอัด ในเทอร์มินัลหนึ่ง
ros2 run go2_control testcase_recorder --ros-args -p case:=pillar_infl035 \
    -p goal_x:=<goal_x> -p goal_y:=<goal_y>

# 5 สั่งเดิน ในอีกเทอร์มินัล
ros2 run go2_control send_mission --goal <goal_x> <goal_y> 0.0

# 6 รอจนหุ่นหยุดนิ่งแล้วเริ่มถอย/หมุนหาทาง นั่นคือจบ ไม่ต้องรอ Nav2 ยอมแพ้
#   Ctrl-C ที่เทอร์มินัลอัด
```

ส่ง goal จาก RViz ก็ได้ ชี้ที่ตัวเสาบนแมพ โหนดอัดจะรับพิกัดจาก `/goal_pose` เอง
ไม่ต้องคำนวณ แต่จะได้ความแม่นระดับที่คลิกเมาส์ได้เท่านั้น

### เลขที่ต้องการ

```text
min_goal_dist_m     ระยะที่กลางหุ่นเข้าใกล้กลางเสาที่สุด  ← ตัวหลัก
                    ลบรัศมีเสาออก = ระยะจากกลางหุ่นถึงผิวเสา
                    เทียบกับ inscribed radius 0.25 ที่คำนวณได้

min_goal_dist_at_s  วินาทีที่เข้าใกล้ที่สุด ใช้หาช่วงใน samples.csv
recovery_log_lines  จะไม่เป็น 0 เพราะ goal ไปไม่ถึง เป็นเรื่องปกติของเคสนี้
```

**ต้องเอาตลับเมตรวัดด้วย** จากผิวเสาถึงเทปกาวที่ติดใต้กลางหุ่นตอนหยุด เพราะ
`min_goal_dist_m` คิดจากตำแหน่งที่หุ่นเชื่อ ไม่ใช่ที่หุ่นอยู่จริง

### ไล่ค่า inflation

**`inflation_radius` ปรับสดไม่ได้** Foxy's InflationLayer อ่านค่าครั้งเดียวตอน
`onInitialize` และไม่มี parameter callback เลย ตั้งจาก panel แล้ว `ros2 param get`
จะเห็นค่าใหม่ แต่หุ่นยังใช้ค่าเก่า ต้อง **relaunch ทั้งสแตก** ต่อหนึ่งค่า

หนึ่งค่า = relaunch หนึ่งครั้ง ราว 5 นาทีรวมตั้ง initial pose ใหม่ ถ้าเวลาไม่พอ
ให้ทำแค่สองค่า 0.35 กับ 0.55 ซึ่งพอบอกทิศทางได้ แยกชื่อ case ตามค่า

```text
0.25   เท่ากับ inscribed พอดี ควรเข้าใกล้ที่สุด
0.35   ค่าปัจจุบัน
0.45
0.55   โซนไล่ระดับกว้างขึ้น 30 ซม. ควรเริ่มชะลอไกลขึ้น
```

เอา `min_goal_dist_m` ทั้งสี่มาเรียง ถ้าไม่ขยับตาม `inflation_radius` แปลว่า
ที่หยุดไม่ใช่เพราะ inflation แต่เป็นเพราะ footprint ชนตรง ๆ ซึ่งเป็นคนละเรื่อง
และ inflation_radius จะไม่ใช่ค่าที่ควรไปปรับ

### ก่อนเคสนี้ต้องวัด footprint จริงก่อน

`footprint` ตอนนี้ตั้งไว้ 0.70 x 0.50 ม. โดยคอมเมนต์ในไฟล์บอกว่าเผื่อ **ขาสวิง**
แต่หุ่นตัวนี้เป็น Go2W ใช้ล้อ ไม่มีขาสวิง ค่านี้จึงไม่เคยตรวจกับหุ่นจริง

เอาตลับเมตรวัดกว้างคร่อมล้อและยาวสุด ถ้าไม่ตรงให้แก้ `footprint` ใน
`nav2_livox_go2.yaml` **ก่อน** เริ่มเทสอย่างอื่น เพราะทุกเลขเรื่องระยะห่าง
สิ่งกีดขวางคิดจากค่านี้

## เคสตรวจตราเต็มรูปแบบ · ทำท้ายวัน ใช้เวลา 1 ชม.

เคสอื่นทั้งหมดทดสอบชิ้นส่วน เคสนี้ทดสอบ**ของที่จะส่งมอบจริง** สั่งจากเว็บ
เดินเอง ถ่ายรูป ส่งรูปกลับ ถ้าเคสนี้ผ่าน แปลว่าระบบใช้งานได้ ไม่ใช่แค่ส่วนประกอบทำงาน

ทำท้ายวัน เพราะต้องให้เคสสั้น ๆ ผ่านก่อน ไม่งั้นแยกไม่ออกว่าอะไรพัง

### รูปเส้นทาง

**ไปแล้วกลับทางเดิม** ไม่ใช่วนเป็นวง

```text
Start → A → B(ถ่าย) → C → D(ถ่าย) → E
      → D(ถ่าย) → C → B(ถ่าย) → A → Start
```

ที่ต้องไปแล้วกลับทางเดิม ไม่ใช่วนเป็นวง เพราะ**แต่ละจุดถูกไปถึงสองครั้ง
จากทิศตรงข้ามกัน** error ของ localisation ขึ้นกับว่าหุ่นหันไปทางไหน ซึ่งเส้นทาง
วงกลมซ่อนไว้หมด เพราะผ่านแต่ละจุดทิศเดียว

ระยะรวมควรได้ 40-60 เมตร ให้กว้างที่สุดเท่าที่ห้องให้ได้ ถ้าสั้นกว่านั้น drift
ยังไม่ทันโผล่

ให้มีอย่างน้อยหนึ่งช่วงที่มองไม่เห็นจุดเริ่ม เช่นอ้อมมุมหรือหลังเสา

### วิธีสั่ง

```bash
# บันทึกเส้นทางก่อน เข็นหุ่นไปยืนทีละจุดแล้วกด
ros2 run go2_control record_waypoint

# เริ่มอัด
ros2 run go2_control testcase_recorder --ros-args -p case:=patrol_lap1

# สั่งจากเว็บจริง ไม่ใช่จากคอมมานด์ไลน์ — นั่นคือทั้งประเด็นของเคสนี้
# ถ้าเว็บยังไม่พร้อม ใช้อันนี้แทนได้ แต่ไม่นับว่าผ่านเคสนี้
ros2 run go2_control send_mission --file missions/patrol.json
```

รันสามรอบติดกัน แยก case เป็น `patrol_lap1` `lap2` `lap3`
**รอบที่ 2 ให้ดึงสาย Wi-Fi ของเครื่องที่เปิดเว็บกลางทาง** แล้วต่อกลับ ทุกอย่างรัน
บนบอร์ดแล้ว หุ่นควรเดินต่อจนจบ และเว็บควรกลับมาเห็นสถานะได้เองเมื่อต่อกลับ

### เลขที่ต้องการ

```text
closing_error_m          ของแต่ละรอบ  โตขึ้นตามรอบไหม
path_map_m / path_odom_m ต่างกันมาก = AMCL กับ FAST-LIO ไม่ตรงกัน
correction_max_jump_m    กระโดดใหญ่ที่สุดตลอดรอบ  นี่คือตัวที่ทำให้หุ่นสะบัด
recovery_log_lines       ยิ่งน้อยยิ่งดี  ถ้าเยอะ ดูใน samples.csv ว่าเกิดตรงไหน
duration_s               เอาไว้เทียบกับรอบอื่น รอบที่ช้ากว่ามากแปลว่ามีอะไรติด
```

### เช็คที่ดีที่สุดของเคสนี้ ไม่ต้องใช้ตลับเมตร

**เทียบรูปสองใบของจุดเดียวกัน** จุด B ถูกถ่ายตอนขาไปและขากลับ สั่งด้วยพิกัด
เดียวกัน ถ้า localisation ดี รูปสองใบควรเกือบทับกัน

เอารูปมาวางซ้อนกันดู ถ้าเลื่อนไปชัดเจน นั่นคือ localisation error ที่มองเห็นได้
โดยไม่ต้องวัดอะไรเลย และเป็นเลขที่ตรงกับสิ่งที่ลูกค้าจะเห็นจริง เพราะสิ่งที่ส่งมอบ
คือรูป ไม่ใช่พิกัด

ทำแบบเดียวกันข้ามรอบได้ด้วย รูปจุด B ของรอบ 1 เทียบรอบ 3

### เรื่องถอยหลัง อ่านก่อนวางแผน

**ตอนนี้หุ่นถอยหลังไม่ได้เลย** `min_vel_x: 0.0` ใน `nav2_livox_go2.yaml`
แปลว่า DWB ไม่มีวันสั่งความเร็วติดลบ ที่เคยเห็นหุ่นถอยคือ recovery behaviour
BackUp ซึ่งสั่งตรงไม่ผ่าน DWB คนละทางกัน

ถ้าจะทดสอบถอยหลังจริงต้องตั้ง `min_vel_x` เป็นค่าติดลบ เช่น -0.15
ปรับสดได้ (อยู่ใน KinematicsHandler เหมือนความเร็วตัวอื่น) แต่ **ไม่ได้อยู่ใน
dev panel และไม่ควรใส่** เพราะเปิดความสามารถใหม่ให้หุ่น ไม่ใช่ปรับค่าที่มีอยู่

คำแนะนำคือ **อย่าเพิ่งเปิดถอยหลังในเคสตรวจตรา** หุ่นตัวนี้ไม่เคยขับถอยหลังเลย
ให้แยกเป็นเคสของมันเอง ทำตอนพื้นที่โล่งและมีคนถือรีโมท เริ่มที่ระยะหนึ่งเมตร

Mid-360 มองรอบตัว 360 องศาอยู่แล้ว ข้างหลังจึงไม่ใช่จุดบอดในแนวนอน
จุดบอดที่มีคือแนวตั้ง ของที่เตี้ยกว่า 25 ซม. ซึ่งเตี้ยเท่ากันทุกทิศ

### อีกอย่างที่ควรดูในเคสนี้

`FollowPath.xy_goal_tolerance` เป็น 0.2 ส่วน `goal_checker.xy_goal_tolerance`
เป็น 0.35 คนละตัวกันและไม่ตรงกัน ตัวแรกเป็นระยะที่ critic RotateToGoal เริ่ม
หันหาทิศสุดท้าย ตัวหลังเป็นระยะที่ถือว่าถึงแล้ว

ให้ดูที่จุดถ่ายรูปว่าหุ่นหันถูกทิศไหม เพราะมุมกล้องคือสิ่งที่ลูกค้าเห็น
ถ้ารูปมุมเพี้ยนบ่อย ๆ สาเหตุน่าจะอยู่ตรงความไม่ตรงกันนี้ ไม่ใช่ที่ตำแหน่ง

## สองอย่างที่ต้องทำทุกเคส ไม่มีข้อยกเว้น

**หุ่นยืนนิ่ง 5 นาที ก่อนเริ่มเคสอื่นของวันนั้น** เป็นเคส 1 ในแผนหน้างาน ได้ค่า
`correction_mean_m` ตอนไม่ขยับ เป็นเส้นฐาน ถ้าไม่มี จะแยกไม่ออกว่า error ที่จุดหมาย
มาจากการเดิน หรือมีอยู่แล้วตั้งแต่ยังไม่ขยับ

**สองรอบขั้นต่ำต่อเงื่อนไข** โปรเจกต์นี้เคยได้ผลกลับด้านระหว่างรอบแรกกับรอบสอง
มาแล้วหลายครั้ง รอบเดียวไม่นับ
