## 0 · MQTT URL ที่ตั้งได้โดยไม่ต้อง build ใหม่

```text
หน้าเว็บนี้ต่อ MQTT broker ผ่าน websocket ด้วยค่า VITE_MQTT_URL ซึ่ง build ติดไป
ในบันเดิล ตอนนี้ชี้ ws://192.168.68.63:9001 ซึ่งเป็นซับเน็ตของไซต์เก่า

IP ของ broker เปลี่ยนทุกครั้งที่ย้าย Wi-Fi ทำให้ต้อง build ใหม่ทุกไซต์
ขอให้เปลี่ยนเป็นตั้งค่าได้ตอน runtime:

- อ่านค่าจาก localStorage ก่อน ถ้าไม่มีจึงใช้ค่าจาก VITE_MQTT_URL เป็น default
- มีช่องกรอกในหน้า settings ให้แก้ URL แล้วเชื่อมต่อใหม่โดยไม่ต้องรีโหลด
- แสดงสถานะการเชื่อมต่อให้เห็นตลอด (connected / connecting / disconnected)
  พร้อม URL ที่กำลังใช้อยู่ ไม่ใช่ซ่อนไว้

หมายเหตุ เบราว์เซอร์ต้องใช้พอร์ต 9001 (websocket) ส่วนหุ่นต่อพอร์ต 1883 (TCP)
คนละพอร์ตแต่เป็น broker เดียวกัน อย่าเผลอกรอก 1883
```

## 0.5 · ขอข้อมูลปัจจุบัน ทำก่อนทุกหน้าจอ

ฝั่งหุ่นรองรับแล้ว

```text
MQTT ส่งให้เฉพาะสิ่งที่ publish ตอนที่เราติดตามอยู่ ของก่อนหน้านั้นไม่ได้เลย
และหุ่นส่งตามรอบของมันเอง แมพทุก 30 วินาที สถานะเฉพาะตอนเปลี่ยน
หน้าที่เพิ่งเปิดหรือเพิ่งรีเฟรชจึงเคยเห็นแมพว่างและหุ่นที่ดูเหมือนไม่ทำอะไร
ทั้งที่มิชชันกำลังเดินอยู่

ทันทีที่ต่อ broker ได้ ให้ publish

  {"action":"get_state"}   ไปที่ `/missions/control`

หุ่นจะส่งทุกอย่างกลับมาใหม่ในครั้งเดียว บน topic ปกติของมันเอง
คือ `/missions/map`, `/missions/pose`, `/missions/params`, statusTopic และ
progressTopic ของมิชชันที่ค้างอยู่ — ไม่ต้องเขียนตัวรับใหม่ ตัวเดิมรับได้เลย

บวกอีกหนึ่ง topic ที่มีเฉพาะตอบ get_state คือ `/missions/state`

  {"hasMission":true, "runId":"r7", "missionId":"m2",
   "paused":true, "stopping":false, "waypointCount":3, "hasMap":true,
   "statusTopic":"web/status", "progressTopic":"web/prog",
   "imageTopic":"web/img", "timestamp":1789095636}

ใช้ยังไง

- ส่ง get_state ทุกครั้งที่ต่อ broker ได้ และทุกครั้งที่ reconnect หลังเน็ตหลุด
  ไม่ใช่แค่ตอนโหลดหน้าแรก
- `hasMission` แยก "ไม่มีมิชชัน" ออกจาก "หุ่นไม่ตอบ" ซึ่งหน้าจอต้องแสดงคนละแบบ
- `paused` ไม่ได้อยู่ใน status ปกติ เป็นที่เดียวที่รู้ว่าค้างอยู่เพราะถูกสั่ง pause
- `hasMap` false แปลว่าหุ่นยังไม่ได้รับแมพเลย ไม่ใช่ว่าส่งมาแล้วเราพลาด
  ให้แสดงคนละข้อความกัน
- หุ่นส่ง state ชุดนี้ให้เองด้วยตอนมันต่อ broker ได้ เผื่อกรณี broker เพิ่งกลับมา
```

## 1 + 2 + 3 · แมพ marker และ zoom/pan

```text
ทำหน้าแสดงแผนที่หุ่นยนต์ ข้อมูลมาทาง MQTT over websocket ฝั่งหุ่นส่งครบแล้ว
ไม่ต้องแก้อะไรฝั่งหุ่น

subscribe topic `/missions/map` — ส่งซ้ำทุก 30 วินาที payload เป็น JSON

  {"width":284, "height":304, "resolution":0.05,
   "origin":{"x":-6.95,"y":-12.2,"yaw":0}, "image":"<PNG base64>"}

  width/height เป็นพิกเซล resolution เป็นเมตรต่อพิกเซล
  origin คือพิกัดโลกของมุมล่างซ้ายของภาพ
  image เป็น PNG base64 พิกเซลที่มีสิ่งกีดขวางเป็นสีเข้ม

subscribe topic `/missions/pose` — ส่งทุก 1 วินาที

  {"x":2.41, "y":-1.08, "yaw":1.57, "frame":"map", "timestamp":1757230000}

  x/y เป็นเมตรในกรอบ map, yaw เป็นเรเดียน (ฝั่งหุ่นแปลงจาก quaternion ให้แล้ว)

สิ่งที่ต้องทำ

1. วาดภาพแมพลง canvas
2. วาง marker หุ่นตามสูตรนี้ ห้ามคิดสูตรเอง

     px = (x - origin.x) / resolution
     py = height - (y - origin.y) / resolution

   `height -` ในบรรทัดที่สองสำคัญมาก เพราะแถวแรกของแมพคือด้านล่างในเชิงพิกัดโลก
   แต่ canvas วาดแถวแรกไว้บน ถ้าลืมจะกลับด้านบนล่างโดยไม่มีอะไรฟ้อง
   และจะไปรู้ตอนเห็นหุ่นเดินทะลุกำแพงเท่านั้น

3. หมุน icon ตาม yaw แปลงเป็นองศาได้เลย
4. ถ้าจะวาดกรอบตัวหุ่น จุด x,y คือกึ่งกลางหุ่นบนพื้น footprint เป็นสี่เหลี่ยม
   0.70 x 0.50 เมตร รอบจุดนั้น หมุนตาม yaw
5. ใช้ timestamp เช็คความสด ถ้าเกิน 5 วินาทีไม่มีข้อมูลใหม่ ให้ marker จางลง
   และขึ้นข้อความว่าข้อมูลค้าง — marker ที่ดูสดแต่จริง ๆ ค้างอยู่ แย่กว่าไม่มี marker
6. zoom ด้วย scroll และ drag เพื่อเลื่อน เป็น transform บนภาพล้วน ๆ
   marker ต้องเลื่อนและซูมไปพร้อมภาพ ไม่ใช่ลอยอยู่คนละชั้น
7. หน้าเพิ่งเปิดจะยังไม่มีแมพจนกว่าจะถึงรอบส่งถัดไป (สูงสุด 30 วินาที)
   ให้ขึ้นสถานะรอ ไม่ใช่หน้าขาว
```

## 4 · Dev testing panel

ข้อนี้ต้องเขียนเพิ่มทั้งสองฝั่ง ฝั่งหุ่นยังไม่รองรับ ให้ทำ UI ไว้ก่อนได้

```text
ทำ panel ปรับค่า Nav2 สดจากหน้าเว็บ ส่งคำสั่งไปทาง MQTT topic
`/missions/control` ฝั่งหุ่นจะเรียก ros2 param set ให้

ค่าที่ต้องมี

  max_vel_x, max_vel_theta, acc_lim_x, acc_lim_theta
  xy_goal_tolerance, yaw_goal_tolerance
  inflation_radius, cost_scaling_factor

สองเรื่องที่ panel ต้องกันไว้ ไม่ใช่แค่หมายเหตุ

  xy_goal_tolerance ห้ามต่ำกว่า 0.35 เมตร ค่านี้ถูกกำหนดด้วยค่าคลาดของ
  localisation ที่วัดได้ 0.258 เมตร ไม่ใช่ความชอบ ตั้งต่ำกว่านี้หุ่นจะวนรอบ
  จุดหมายที่ไปถึงแล้วไม่จบ ให้ panel กันไว้และอธิบายเหตุผลตรงนั้น

  ความเร็วสูงสุดจริงถูกตัดอีกชั้นที่ unitree_udp_bridge ด้วย --max-linear และ
  --max-angular ซึ่งไม่ใช่ ROS parameter ปรับสดไม่ได้ ต้องรีสตาร์ท และการตัด
  ของมันชนะ Nav2 เสมอ panel ต้องแสดงค่าสองตัวนี้ไว้ข้าง max_vel_x ให้เห็น
  ไม่งั้นจะตั้ง Nav2 ไว้ 0.40 แล้วงงว่าทำไมหุ่นวิ่ง 0.25 ซึ่งเกิดขึ้นมาแล้วหน้างาน
```

## 4b · ปุ่ม Apply สำหรับค่าที่ต้องรีสตาร์ท

ต่อจากข้อ 4 · ฝั่งหุ่นกำลังทำ รอผลทดสอบก่อนว่าใช้ได้จริงไหม

```text
ตอนนี้มี 14 ตัว แบ่งเป็นสองพวกตามฟิลด์ `applies` ที่หุ่นส่งมา

  live      สี่ตัว   ปรับแล้วมีผลรอบถัดไปเลย ไม่ต้องทำอะไรเพิ่ม
  restart   สิบตัว   ค่าถูกเก็บไว้ แต่หุ่นยังใช้ค่าเก่าจนกว่าจะสั่งให้โหนดเริ่มใหม่

กลุ่ม AMCL หกตัว เพิ่มเข้ามาใหม่ ทุกตัวเป็น restart

  update_min_d   update_min_a   min_particles   max_particles
  laser_max_range   transform_tolerance

  min_particles กับ max_particles เป็น **จำนวนเต็ม** ไม่ใช่ทศนิยม
  และหุ่นจะปฏิเสธทั้งคู่ถ้า min มากกว่า max

สำหรับพวก restart ให้ทำปุ่ม Apply แยกต่างหาก ไม่ใช่มีผลทันทีที่เลื่อน slider

  {"action":"set_params","params":{"inflation_radius":0.55},"restart":true}

ใส่ `"restart": true` เพิ่มเข้าไปในคำสั่งเดิม หุ่นจะตั้งค่าแล้วสั่ง controller_server
ให้เริ่มใหม่ให้ วัดกับ AMCL แล้วใช้เวลาราวหนึ่งในร้อยวินาที แต่ให้เผื่อไว้ 2-3 วินาที
แล้วตอบกลับที่ `/missions/params` ตามปกติ พร้อม `notes` ที่บอกว่าหมุนสำเร็จไหม

สิ่งที่ UI ต้องทำ

1. slider พวก restart เลื่อนแล้ว **ยังไม่ส่งอะไร** ให้ขึ้นสถานะว่า "รอ Apply"
   และแสดงค่าเก่าที่หุ่นใช้อยู่คู่ไปด้วย ให้เห็นว่ากำลังจะเปลี่ยนจากอะไรเป็นอะไร

1b. ใช้ฟิลด์ `cycles` ที่หุ่นส่งมา จัดกลุ่ม slider ตามโหนดที่ต้อง cycle
   แล้วทำ **ปุ่ม Apply หนึ่งปุ่มต่อกลุ่ม** ไม่ใช่ปุ่มเดียวรวมทุกอย่าง

     /amcl               กลุ่ม AMCL หกตัว
     /controller_server  Goal สองตัว + Costmap สองตัว

   สำคัญเพราะการกด Apply ของกลุ่ม AMCL ไม่ควรไปแตะ controller_server
   ซึ่งเป็นเส้นที่ฝั่งหุ่นยังไม่ได้ทดสอบ ส่วน /amcl ทดสอบกับสแตกจริงแล้ว

2. **ห้ามกดตอนหุ่นกำลังเดิน** ให้ disable ปุ่มเมื่อ `/missions/state` บอกว่า
   `hasMission` เป็น true หุ่นจะปฏิเสธเองอยู่แล้วและตอบมาใน `notes`
   แต่ปุ่มที่กดได้แล้วโดนปฏิเสธ แย่กว่าปุ่มที่กดไม่ได้

3. ระหว่างหมุน ให้ขึ้นสถานะกำลังดำเนินการและ disable ทั้ง panel
   ถ้า marker หยุดอัปเดตชั่วขณะ อย่าแสดงเป็นว่าหุ่นหายไป
   ให้บอกว่ากำลังตั้งค่าใหม่

4. เมื่อ `/missions/params` ตอบกลับมา ให้อ่าน `values` แล้ววาดใหม่
   ถ้าค่าไม่เปลี่ยนตามที่ขอ แปลว่าล้มเหลว ให้ดู `notes`

5. ถ้าไม่มีอะไรตอบกลับใน 30 วินาที ให้ถือว่าล้มเหลว ขึ้นข้อความให้ผู้ใช้
   ตรวจสอบหน้าจอที่หุ่น อย่าปล่อยให้ค้างเงียบ ๆ

6. ถ้า `notes` มีคำว่า FAILED ให้ขึ้นเป็นคำเตือนแดง ไม่ใช่ข้อความธรรมดา
   แปลว่า controller_server ค้างอยู่ครึ่งทางและหุ่นขับไม่ได้จนกว่าจะมีคนแก้ที่เครื่อง

ค่าสองตัวของ bridge ยังปรับไม่ได้อยู่ดี แม้จะกด Apply
ต้องรีสตาร์ท process เอง ให้แสดงเป็นอ่านอย่างเดียวต่อไป
```

## 5 · โหมด

## 6 · แบต

ต้องเขียนเพิ่มทั้งสองฝั่ง ฝั่งหุ่นอ่านค่าได้แล้วแต่ยังไม่ส่งขึ้น broker

```text
แสดงระดับแบตเตอรี่หุ่นบนหน้าหลัก และเตือนเมื่อลดต่ำระหว่างมิชชัน

ถ้าไม่มีข้อมูลแบตเข้ามาเลย ให้แสดงว่าไม่มีข้อมูล ไม่ใช่แสดง 0%
```
